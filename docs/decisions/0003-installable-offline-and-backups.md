# 0003. The app installs from a project base path, precaches everything, and backs up as one file

Date: 2026-09-22 · Status: accepted; base path and Pages deploy superseded by 0007 · Tracker: E2 — Install it, and keep the data

## Context
0002 chose a local-first PWA and named the debt it left: the log lived only in a Safari tab, in
storage iOS is free to evict, reachable only with a signal. The gym has no signal. Nothing could
take the data off the phone. E2 is that debt.

Two facts shape the answer. The host is a public GitHub repository, so the only free deployment
is GitHub Pages — which serves a project site from `/WorkoutTracker/`, not a domain root. And
the target is iOS Safari, where a web app is installable but gets no background execution, no
reliable notifications, and no guarantee its storage survives.

## Decision
- **Served from `/WorkoutTracker/`.** `base` is set once in `vite.config.ts`; every asset
  reference, the manifest's `start_url` and the service worker's scope carry it. A static build
  deploys from `.github/workflows/deploy.yml`.
- **Installable**: `manifest.webmanifest` with `short_name: "Workout"`, `display: standalone`,
  a theme colour, and 192/512 icons including a maskable one, generated by a committed script.
- **`vite-plugin-pwa` with `registerType: 'prompt'` and `injectRegister: null`.** The app owns
  registration. Everything the app needs is precached; there is no runtime caching, because
  there are no network calls to cache.
- **A new version never takes over mid-session.** When the worker finds an update the app
  carries on untouched and offers an "Update ready" control. `skipWaiting` runs only when that
  control is pressed; nothing reloads on its own.
- **Backup is one plain JSON file** — `workout-backup-<yyyy-mm-dd>.json`, `schemaVersion: 1`,
  every session plus the settings. It goes through the share sheet where the browser offers
  one, and a download link where it does not.
- **Import replaces the whole database**, after taking a fresh export first and refusing to
  write at all if that export fails. A counted confirmation names how many sessions are here,
  how many are coming, and how many will go. An unknown `schemaVersion` is refused, not guessed.
- **The reminder is a badge at 14 days** on the settings entry — strictly more than 14, and a
  never-exported database counts as due. Never a modal, a toast or a notification.

## Alternatives rejected
- **`registerType: 'autoUpdate'` / `skipWaiting` on discovery**: swaps the app out underneath a
  half-logged set. The one failure this design exists to prevent.
- **Merging two databases by session id, or newest-wins**: needs conflict resolution and implies
  a second device, which is a stated non-goal. Replace-after-export is honest about what it does.
- **Automatic or scheduled backups**: iOS gives an installed web app no reliable background
  execution. A backup that silently does not happen is worse than a badge that asks.
- **A modal or notification reminder**: it would stand between the trainee and starting a
  workout, for something that can wait until after the session.
- **Migrating older `schemaVersion`s**: there is only version 1. Guessing at a format that has
  never existed is speculative code that can only be wrong.

## Consequences
- **The service worker's first install needs one online visit.** A phone that has never loaded
  the app online cannot cold-start it offline. This is inherent to service workers.
- **iOS can still evict IndexedDB.** Export is the recovery and the badge is the nudge, but
  nothing forces a backup — a trainee who ignores the badge for a month can still lose a month.
- **Deployment is now two-stage.** GitHub registers `workflow_dispatch` only from the default
  branch, so the workflow had to land on `main` separately before any other ref could deploy,
  and the `github-pages` environment allows only listed branches.
- **The base path is load-bearing.** A build without it serves a white page at the project URL,
  with no error — which is exactly what happened when `main` deployed before E2 merged.

## Outcome
Built across E2-T1..T8 on `epic/E2-install-and-keep-the-data`; see the pull request for the
task-by-task table. 22 test files, 231 tests, lint clean at the epic head.

Where it departed from the decision above, and why:

- **`E2-T8` did not exist when the epic was planned.** E2-T4, E2-T5 and E2-T6 each placed
  `src/App.tsx` out of scope and deferred the wiring to one another, so the whole backup feature
  shipped correct, tested and *unreachable* — `App` passed neither `onExport` nor
  `onImportFile`, `ImportConfirm` was rendered by nothing, and the Export button on screen did
  nothing when pressed. Every task passed its gates honestly; each outcome was testable one
  level below the wiring. Found by hand while writing this record and fixed as an eighth task
  with three integration outcomes driven through the rendered controls.
- **`importBackup(text)` is not in any ticket's interface.** It was added by E2-T5 because O10
  ("when it is imported, then an error names the problem and not one session changes") needed a
  production seam that both parses and writes; testing `readBackup` alone would have passed the
  moment it was written. E2-T8 then routes the confirmed import through it, at the cost of one
  re-parse, so the codebase keeps a single write path.
- **`downloadOrShare`'s object-URL branch is feature-detected.** jsdom provides neither
  `navigator.share` nor `URL.createObjectURL`, and O9's mandatory pre-import export made
  E2-T4's round-trip test call it for the first time. The guard is unreachable in real browsers,
  but it does mean that in an environment with neither capability an import would proceed with
  no backup taken while recording one — softening O9 in principle. Flagged for review.
- **[O3] was never red.** E2-T1's `VitePWA` defaults already precached the shell, assets, icons
  and manifest, so all seven O3 tests passed at E2-T2's red commit; its red rests on two
  registration tests. Making O3 red would have meant removing behaviour E2-T1's own outcomes
  require. The tests are kept as regression locks.
- **`main.tsx` no longer registers the worker.** E2-T3 made `useServiceWorkerUpdate` the single
  owner rather than guard against double registration, because a module-level guard leaked
  across tests. `App` was split into a thin wrapper over `AppViews` so the pill survives every
  view.
- **After a confirmed import, the on-screen active program and backup badge show pre-import
  values until the app is reopened.** No outcome asks for a refresh; left deliberately.
- **`.github/workflows/deploy.yml` has no test**, and never will — asserting on YAML would be a
  change detector. It was verified by hand after merge.
- **One full-suite run failed 1/231 immediately after E2-T8 merged and never recurred in seven
  runs.** The captured stderr named an error only `catalog.test.ts` produces, deliberately and
  caught, in a file that renders no React — most likely interleaved output from parallel
  workers, which means it does not identify the failing test. Not attributed, not reverted,
  recorded.
